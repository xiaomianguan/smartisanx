# 组件核对记录

**中文** · [English](ComponentVerification.md)

这份文档记录把 smartisanx 的组件逐个对照原始实现核对的结果：
对照对象优先是三个复刻项目（同为 Compose，可直接比对），
其次是从原厂 APK 反编译出来的自定义 View 与资源。

核对方法：对每个组件找出原始实现，逐项比对**尺寸常量、几何、时长、缓动、手势物理与所用资源**，
而不是只看「像不像」。

## 二、已知差异（有意为之）

这些地方本库与原版**故意不同**，都已在对应组件的 KDoc 里注明：

| 项目 | 原版 | 本库 | 原因 |
| --- | --- | --- | --- |
| 标题栏高度 | 音乐 50dp / 天气与时钟 48dp | 48dp | 三个应用本身就不一致，取多数；需要 50dp 时传 `contentHeight = 50.dp` |
| 深色模式 | 原版没有 | 实验性，默认关闭 | 由复刻项目新增，且原版素材只有约 2.5% 带夜间变体 |
| 文字 / 提示色 | `editor_text_color` 等取自 framework | 主题语义色 | 这些资源只在 Smartisan framework 里，拿不到 |
| 光标条 | nine-patch `edittext_cursor_bbackground` | 主题 `accent` | Compose 的 `cursorBrush` 只接受 `Brush` |
| 清除按钮显隐 | `setVisibility` 瞬时切换 | 默认 200ms 淡入淡出 | 可传 `animateClearIcon = false` 完全对齐原版 |
| 滚动条 | 系统默认滚动条 | 自绘细滚动条 | 原版没有对应位图 |
| 文字标签栏 | 原版没有文字标签栏 | 自绘 | 原版标签切换都是图标式 |
| 分组标题底色 | framework `#f5f5f5` | 主题 `surfaceRaised`（浅色 `#F7F8F9`） | 深色模式要跟随主题；浅色下与原版相差 ≤3 级灰阶 |
| 分组标题文字色 | framework `#4c000000`（30% 黑） | 主题 `textTertiary`（`#66000000`，40%） | 用主题语义色，并与 `SmartisanGroup` 的分组标题保持同一档 |
| 行说明文字色 | framework `#80000000`（50% 黑） | 主题 `textTertiary`（`#66000000`，40%） | 与 `SmartisanListItem` 的说明文字同一档，避免同一库内两套灰 |
| 行禁用文字色 | framework 不透明 `#bababa` | 主题 `textDisabled`（`#4c000000`，30% 黑 ⇒ 白底约 179） | 用主题语义色；与原版相差不到 8 级灰阶 |
| 编辑行提示文字色 | framework `#26000000`（15% 黑 ⇒ 白底约 217） | 主题 `textHint`（`#DBDBDB` ⇒ 219） | 用主题语义色；只差 2 级灰阶 |
| 带图标滑杆的端点图标 | 两个图标「要么都给、要么都 GONE」（`leftIconRes > 0 && rightIconRes > 0` 才 `setImageResource`） | 两个独立可选槽位，给哪个画哪个 | 槽位式 API 更自然，原版那样更像实现疏漏 |
| 滑杆禁用时的端点图标 | 只切换滑块素材，图标不跟着变灰 | 同左（库不做任何处理） | 保持原版行为；图标要不要变灰由调用方决定 |
| 复合标题栏中槽的自然宽度 | Android 先按 `wrap_content` 量一次再决定居中 | 用 `maxIntrinsicWidth()` 取自然宽度（Compose 只允许量一次） | 自定义 `Layout` 没实现固有测量时按「装不下」处理 |
| 复合标题栏右侧按钮 | 内置最多 10 个 `SmartisanButton`，相邻 `-6dp` 压住 | 不做按钮容器，`trailing` 槽自己排 | 原版那套按钮样式与图标表已由 `SmartisanButton` / `SmartisanIconButton` 覆盖，容器逻辑没必要内建 |
| 消息输入栏文字 / 提示色 | framework `editor_text_color`（#cc000000）/ `editor_hint_text_color`（#26000000） | 主题 `textPrimary` / `textHint` | 跟随 smartisanx 深色主题，与其它输入类组件一致 |
| 消息输入栏的文字监听 | `beforeTextChanged` / `onTextChanged` / `afterTextChanged` 三段回调 | 合并为 `onValueChange` | Compose 只有单一变化回调，前两段没有对应物 |
| 消息输入栏的导航栏 insets | 原版不处理（各 App 布局自己负责） | 同样不处理，由调用方加 | 保持原版的分工 |
| 进度弹窗的圆环动画 | 用平台默认的不确定 ProgressBar（`ProgressBarCircleStyle.Medium` 没指定 drawable） | 用 ROM 里那张 48dp 圈素材匀速旋转（1s/圈，可传参改） | Compose 没有平台不确定动画，素材与尺寸都照原版 |
| 进度弹窗的确定进度 | `setProgress(int)` 是空实现 | 同样只做不确定态 | 原版本身就不支持确定进度 |
| BHM 行的禁用态 | `BHMDrawerItem.isEnabled()` 只挡点击，变灰靠各 App 自己传色 | 同样只挡点击与图标 selector，标题灰由 `SmartisanBhmItem.titleColor` 决定 | 保持原版分工 |
| BHM 的分组标题色 | `bhm_header_view_color` #4d000000（30% 黑） | 主题 `textTertiary`（40% 黑） | 跟随深色主题 |
| BHM 的列表底色 | 布局写死 `@android:color/white` | 主题 `surface` | 跟随深色主题 |

## 三、资源与字体的核对

- **图形资源**：全部来自原厂 APK 的 `res/drawable*` / `mipmap*`，按内容去重，
  保留原始文件名与夜间 / 多密度限定符目录。
- **字体**：正文用 Smartisan OS 系统字体 `Smartisan Compact CNS`，
  取自坚果 R2 官方 ROM 转储的 `system/system/fonts/`；
  字体内嵌名称与字重已通过解析 OTF `name` 表核对（family = `Smartisan Compact CNS`）。
- **图标**：把 selector 链解析到最底层位图后分类，
  排除了 2195 个 nine-patch 按钮底图与 1647 张大图，只保留真图标。

## 四、真机逐像素核对

环境是 macOS + 一台 1264×2800 @ 560dpi 的测试机（即 **3.5px/dp**），
所以现在可以把组件装到真机上截图、**按像素反推实际尺寸与颜色**，不再只靠读数值。
做法：对截图做行 / 列扫描（取第一个与最后一个「有墨」的像素、色带边界与灰度），
再与 framework 的 dimens / colors 对照。

### selector 状态不重绘（示例应用「整页布局」暴露的坑）

原版把 selector 位图设成 `View.background` / `ImageView`，状态一变系统自己会重绘；Compose 里换
`Painter` 不会。真机现象：多选列表点一行后语义树里 `checked` 已经是 `true`，圆圈还是空心的；
按键 / 标题栏图标的按下态也不出现。逐层查下来是两件事叠在一起（都对 Compose UI 1.12.1 的字节码核对过）：

1. `Image(painter)` 内部是 `PainterNode`，而 `PainterNode.getShouldAutoInvalidate()` 是 **false**，
   换 painter 实例、改 drawable 状态都不会触发 `invalidateDraw()`；
2. 绘制阶段读 snapshot 状态的观察者回调是 `coordinator.layer?.invalidate()`，元素更新走的
   `invalidateDraw()` → `NodeCoordinator.invalidateLayer()` 也只会沿着 `wrappedBy` 往外找 layer。
   `Image` 自己那层 `clipToBounds()` 的 layer 一旦建好就没人 invalidate，于是永远画缓存里的旧图。

修法：`Modifier.smartisanRepaintOnStateChange(stateKey)` = `graphicsLayer().drawBehind { stateKey }`
（layer 建在绘制块**前面**，绘制块闭包捕获状态指纹 → 元素变化 → `invalidateDraw()` 命中 layer），
`SmartisanIcon` / `SmartisanIntrinsicImage` 再按状态指纹换 `key` 重建里面的 `Image` 节点
（视觉不变，只是让那层缓存重录），`smartisanPainterBackground` / `smartisanDrawableBackground` /
`smartisanShadowBackground` 同样带上状态指纹。

真机复测（nubia P0110，560dpi，浅色）：

| 项 | 修前 | 修后 |
| --- | --- | --- |
| 「整页布局 → 多选编辑」点「周会纪要」后的勾选框 | 语义 `checked=true`，画面仍是空心圆，整块区域像素差 **AE = 0** | 24dp（84px）图案框里出现实心圆 + 白勾：实测圆 56px、圆心像素 `#D56155`（P3 截图里的 accent） |
| 计算器「=」键按住 / 抬起两帧 | —— | 两帧差异 86155px（2.4%）：按下态底图出现 ✓ |
| 「设置 → 声音与振动」点「静音」行 | —— | 勾从「清澈」移到「静音」✓（同一帧内两个 drawable 都重绘） |
| 列表行 `state_pressed` 底图 | 不重绘 | 重绘（`smartisanDrawableBackground` 带状态指纹） |

### 截图颜色是 Display P3

## 五、标题栏投影的位置（在坚果 R2 上复测）

标题栏下方那 14dp 投影必须是**盖在内容上**的：它画在标题栏边界之外、叠在内容之上，
内容紧贴标题栏下沿开始。原版在 `smartisanos.widget.BarsHelper.BarShadowBuilder` 里是这么做的：

```java
shadow.setTranslationY(mIsBottomType ? -mBottomShadowHeight : mTopShadowHeight);  // 平移出自己的边界
parent.setClipChildren(false);                                                    // 允许画到边界外
mTargetView.setElevation(0.1f);                                                   // 标题栏画在内容之上
```

`SmartisanTitleBar` / `SmartisanTitleBarSurface` 用「贴住栏底边 + `offset(y = TitleBarShadowHeight)`
的子 View」还原同样的效果，`SmartisanScaffold` 再给标题栏 `zIndex(1f)`，对应原版的 `setElevation(0.1f)`。
早先的实现把投影当成普通子 View 排进布局，结果内容被多顶下去 14dp，栏与内容之间留下一条空白带。

实测环境：坚果 R2（`darwin`，1080×2340，`ro.sf.lcd_density=560`，即 3.5px/dp），

## 七、滚动越界回弹（在原版 R2 与测试机上各量一遍）

原版的滚动越界**不是** Material 的拉伸，而是刚性平移 + 匀减速滑行 + 四元缓出回弹。
先把 R2 的 framework 挖开对常数，再在 R2 上录像量行为，最后用同一套脚本量本库在测试机
（nubia P0110）上的实现。

### 1. 原版 framework 的常数（坚果 R2，`android.widget.AbsListView`）

```java
static final int OVERSCROLL_LIMIT_DIVISOR = 3;            // 常量声明（本类里没被引用）
protected void onLayout(...) {
    int i2 = b - t;                                       // 视图高度
    this.mOverscrollDistance = i2;                        // 拖拽上限 = 整屏高
    this.mOverflingDistance = i2 / 2;                     // 甩动上限 = 半屏高
    this.mOverscrollMax = (b - t) / 3;                    // 越界上限 = 1/3 屏高
}
```

`ScrollView.java` 里同一段被包在 `ScrollViewSmtEx.mSmartisanosOverScrollEnable` 里
（只对 `com.buzzfeed.android` 关掉），说明这是**系统级**行为，不是某个 app 自己做的。

回弹这条在 `framework.jar` 的 `android.widget.OverScroller` 里（jadx 反编译 `classes3.dex`）：

```java
static final float GRAVITY = 8000.0f;                     // AOSP 是 2000

private void startSpringback(int start, int end, int velocity) {
    int delta = start - end;
    this.mDeceleration = getDeceleration(delta);          // ±GRAVITY
    this.mVelocity = -delta;
    this.mOver = Math.abs(delta);
    this.mDuration = ((int) (Math.sqrt(((double) delta) * (-2.0d) / ((double) this.mDeceleration))
        * 1000.0d)) + (Math.abs(velocity) / 10);          // = sqrt(2·Δ/GRAVITY)·1000 + |v|/10
}

// update()，state == 1（回弹）：四元缓出
distance = ((double) (this.mOver * sign)) * (1.0d - Math.pow(1.0f - t2, 4.0d));

// 甩到边界：startBounceAfterEdge → onEdgeReached()，先匀减速滑行（state == 2，BALLISTIC）
private void onEdgeReached() {
    float velocitySquared = mVelocity * mVelocity;
    float distance = velocitySquared / (Math.abs(this.mDeceleration) * 2.0f);   // v²/(2·GRAVITY)
    if (distance > mOver) {                               // 超过允许值就把减速度放大到刚好停住
        this.mDeceleration = ((-sign) * velocitySquared) / (i2 * 2.0f);
        distance = i2;
    }
    this.mOver = (int) distance;
    this.mDuration = -((int) ((this.mVelocity * 1000.0f) / this.mDeceleration));
}

// continueWhenFinished() 里还有原厂加的一句：允许值按速度缩放
this.mOver = Math.round((this.mOver * Math.abs(this.mVelocity)) / OverScrollerSmtEx.mMaximumVelocity);
```

也就是：**回弹是四元缓出 `(1-t/T)^4`，时长 `T = sqrt(2·Δ/GRAVITY)`**；
**甩到边界时先按 `v²/(2·GRAVITY)` 匀减速滑行，滑行上限还要按 `|v| / mMaximumVelocity` 缩放**
（mMaximumVelocity = `ViewConfiguration.getScaledMaximumFlingVelocity()` = 8000dp/s × 密度）。

### 2. R2 上的实测（1080×2340 @400dpi，设置页 ListView 高 2100px）

`screenrecord` 逐帧抓、用 `ffmpeg` 重采样到 60fps，按行的 1px 分隔线切行、量「第一行文字带
的中心」位移（脚本与本库测试机共用）：

| 手指位移 | 内容位移 | 比值 |
| --- | --- | --- |
| 400px | 125px | 0.31 |
| 800px | 302px | 0.38 |
| 1200px | 398px | 0.33 |

→ **拖拽阻尼 1/3**（差值来自触摸 slop 与注入事件的分辨率）。

回弹曲线逐模型拟合，这次量了两条（拖拽松手峰值 540px、甩动峰值 523px）：

| 模型 | 拖拽松手（540px） | 甩动（523px） |
| --- | --- | --- |
| 四元缓出 `(1-s)^4`（framework 里那条） | T = 408ms，rms **6.99px** | T = 394ms，rms **5.75px** |
| 临界阻尼弹簧 `(1+ωs)e^{-ωs}` | ω = 20.4，rms 8.31px | ω = 21.0，rms 7.49px |
| 三次缓出 `(1-s)^3` | T = 360ms，rms 8.47px | T = 384ms，rms 6.73px |
| 指数衰减 `e^{-s}` | τ = 70ms，rms 11.20px | τ = 70ms，rms 11.80px |

→ **四元缓出完胜**，与 framework 源码一致；拟合出的 T 与公式 `sqrt(2·Δ/8000)·1000`
（540px → 367ms、523px → 362ms）相差 10% 以内。**这条纠正了上一版记录**：上一版只量了一条
曲线，而且拟合时用的是「进度」`1-(1-s)^4` 而不是「剩余」`(1-s)^4`，于是误判成弹簧更准。

另外量到：

- 全程**行距恒定 150px**（卡片高度、行间距都不变）= 刚性平移，不是拉伸；
- 拖拽松手回弹**从静止开始**（速度序列先涨后落，释放速度不参与回弹）；
- 甩动（手指 1200px / 100ms）**不是停在松手点**，而是继续滑行：位移 94 → 523px 用了 87ms，
  且每 20ms 的增量递减（180 / 95 / 45 / 39px）= 匀减速；523px 对得上
  半屏高 1050px × |v|/20000（v ≈ 9000px/s → 472px）。

### 7. 示例应用的分组卡片复查（2026-10-11）

把示例应用里「组件直接落在条纹底纹上」的地方全部收进卡片。`SmartisanGroup` **默认是透明的**
（卡片底图由内容自己画），所以内容是自定义排版的（色板、按钮排排站、表盘、输入框、开关排、
形状排……）必须显式传 `position`：

- **40 处**补 `position = SmartisanGroupRowPosition.Single`（按钮 / 时钟 / 时钟刻度 / 图标 /
  输入 / 布局 / 浮层 / 文本 / 原版控件 / 原版布局等页，脚本按行号精确替换）；
- 主题页的深浅色单选组、「实验性提示」卡片、色板 / 文字样式 / 形状三张卡片、侧滑两处共
  **9 处**手工补；
- 内容是列表行的**改成按位置取底图**：`SmartisanListItem` → `SmartisanGroupItem`
  （时钟页 3 行、布局页 6 行、浮层页 12 行），`SmartisanListRow` → 页内 `MatrixRow`
  （矩阵 7 组 14 行），侧滑行自己画底图（行是前景，必须不透明，否则删除动作会透出来）。
- 首页与「基础控件」页原本就是对的（行按 Top / Middle / Bottom 取三段底图），这次以它们为样板。

复查后 `SmartisanGroup` 共 75 处：46 处带 `position`，另外 29 处的内容都是自己画卡片的行，
没有一处再直接落在底纹上。

「关于」页的 logo 卡片原来比下面的列表卡片**窄 11dp**（实测 x = 85..1178 vs 46..1217）：
它用的是设置页子项那张 `sub_item_back_ground_single` 9-patch，素材**自带的透明边距**
就有 37px = 12.3dp，再叠上 12dp 外边距，卡片两侧缩到 24.3dp。原版「关于本机」页里 logo 卡片
（`ListContentItemStyle.Single`）与五行设置行同属 `ListContentItemStyle` 一族、两张卡片一样宽
（坚果 R2 实测两张都是 x = 30..1049，即左右各 12dp）。改用与列表行同一张
`group_list_item_bg_single`（白色 + 10dp 圆角 + 1px 描边）+ `list_content_item_single_shadow`
之后，实测 logo 卡片 x = 43..1220、列表卡片 x = 42..1220（差 1px 是量点落在 10dp 圆角上的缘故）。

同一张卡片里的三行文字又按项目自己的样子重排了一次：原版图里「smartisan os」与
